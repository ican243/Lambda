2편 — 코드 해석편

여기 나오는 코드는 전부 지금 이 순간 실제 파일에서 그대로 뽑아온 것입니다.
손으로 옮겨 적지 않고 빌더가 파일을 직접 읽어 넣었으므로 오타나 옛날 버전이 섞일 수 없습니다.

읽는 법
① 검은 코드 박스 = 진짜 코드 (왼쪽 숫자는 실제 파일의 줄 번호)
② 파란 박스 🔍 = 그 줄이 무슨 뜻인지, 왜 그렇게 짰는지
개념·용어가 막히면 1편 개념·구조편을 같이 펴 두세요.
🔒 비밀값은 자동으로 가려집니다
config/db.php의 DB 비밀번호, kis_config.php의 KIS 앱키·시크릿은 빌더가 빌드할 때 자동으로 ••••••••[마스킹됨]로 바꿉니다. 빌드 마지막에 결과물 전체를 다시 훑어 비밀값이 남았는지 검사하고, 남아 있으면 빌드를 실패시킵니다. 그래서 이 문서는 남에게 보여줘도 안전합니다.

CODE 1DB 연결과 타임존

모든 PHP가 여기서 시작합니다. 21줄짜리 작은 파일인데, 뒤쪽 절반이 이 프로젝트에서 가장 중요한 3줄입니다.

🔍 줄 해석
  • 5~8 접속 정보. 여기가 바뀐 부분입니다 — 예전엔 localhost/stock_db였는데 지금은 원격 공용 DB입니다. 비밀번호는 빌더가 가렸습니다.
  • 10~14 연결 시도. 실패하면 die()로 즉시 멈춥니다. DB 없이 페이지를 반쯤 그리는 것보다 명확히 죽는 게 낫습니다.
  • 16 문자셋을 utf8mb4로. 이걸 안 하면 한글 종목명이 깨집니다.
  • 18~ 이 파일의 핵심. 원격 DB 서버 시계는 UTC인데 우리 데이터·로직은 전부 KST입니다. 세션 타임존을 고정하지 않으면 새로 들어가는 행이 9시간 뒤로 찍혀서 "오늘" 조회·정렬·집계가 전부 어긋납니다.
새 DB 접속 코드를 만들면 반드시 같이 걸 것. Node 쪽도 stock-ws/db.js에서 똑같이 SET time_zone='+09:00'을 겁니다(CODE 22). PHP와 Node가 같은 시계를 봐야 분봉 키가 맞습니다.

비밀이 담긴 폴더는 웹으로 열리면 안 됩니다. 한 줄짜리 방어지만 없으면 끝입니다.

🔍 줄 해석

  • 19~22 옛 Apache(2.2)에서도 동작하게 폴백. 서버 버전을 모를 때 두 가지를 다 써두는 게 안전합니다.

실제로 뚫려 있었습니다. stock-ws/.env에는 DB 비밀번호와 KIS 시크릿이 들어 있는데, 한동안 웹에서 200으로 열렸습니다. 지금은 막았지만, 이 PC를 외부에 노출한 적이 있다면 비밀번호와 KIS 시크릿을 교체하는 게 안전합니다.

CODE 3운영 공통층 — 스키마 자동 생성

"형이 SQL을 직접 돌려야 함"을 없애는 장치입니다.

🔍 줄 해석
  • CREATE TABLE IF NOT EXISTS — 이미 있으면 조용히 넘어갑니다. 그래서 몇 번을 호출해도 안전합니다(멱등).
  • INSERT IGNORE ... app_settings — 기본 설정값 3개를 심습니다. IGNORE라서 이미 형이 바꿔둔 값을 덮어쓰지 않습니다. 이 한 단어가 "초기화"와 "복구"를 가릅니다.
  • access_logs에 인덱스 3개(ip·user·created) — 나중에 "이 IP가 언제 뭘 했나"를 빠르게 찾기 위한 준비입니다.
  • 왜 이렇게까지 하나: 배포 절차에 수동 SQL 단계가 있으면 다음 세션에서 잊힙니다. 실제로 이 프로젝트에서 마이그레이션 파일 때문에 한 번 크게 헤맸습니다(ADD COLUMN IF NOT EXISTS는 MariaDB 전용).

CODE 4CSRF 방어

"로그인된 형의 브라우저를, 다른 사이트가 시켜서 우리 서버로 요청을 쏘게 하는" 공격을 막습니다.

[CSRF 공격 시나리오] ① 형이 우리 사이트에 로그인 (세션 쿠키 보유) ② 형이 악성 사이트 방문 ③ 악성 사이트가 숨겨진 폼으로 우리 서버에 POST → 브라우저는 쿠키를 "자동으로" 같이 보냄 → 서버 입장에선 형이 보낸 요청과 구별이 안 됨 ⚠️ [막는 원리] 세션 안에만 있는 난수 토큰을 폼에 심고 서버에서 대조. 악성 사이트는 우리 세션 내용을 읽을 수 없으므로 토큰을 만들 수 없다.
🔍 줄 해석
  • bin2hex(random_bytes(32)) — 암호학적으로 안전한 난수 64자. rand() 같은 건 예측 가능해서 쓰면 안 됩니다.
  • 토큰을 세션에 저장하고 폼에는 사본을 심습니다. 세션은 서버에 있어 외부에서 못 읽습니다.
  • $_POST['csrf_token'] ?? $_SERVER['HTTP_X_CSRF_TOKEN'] — 폼 제출과 fetch(JSON) 양쪽을 다 받습니다. 헤더로도 보낼 수 있게 열어둔 것입니다.
  • hash_equals()가 핵심 — 일반 ==는 첫 글자가 다르면 즉시 끝납니다. 그 응답 시간 차이로 토큰을 한 글자씩 알아낼 수 있습니다(타이밍 공격). hash_equals는 항상 같은 시간이 걸립니다.
🔍 줄 해석
  • 맨 처음 REQUEST_METHOD !== 'POST'면 그냥 통과 — 조회(GET)에는 CSRF 검사가 필요 없습니다. 상태를 바꾸지 않으니까요.
  • $mode='json' — 화면 이동이 필요 없는 fetch 요청에는 403 + JSON으로 답합니다. 폼 제출에는 리다이렉트로 답합니다. 같은 방어를 두 가지 방식으로 낼 수 있게 만든 것입니다.
  • 마지막 exit가 중요합니다. 안 붙이면 차단해놓고 아래 코드가 계속 실행됩니다.

CODE 5접속 로깅 — FDS의 기초

🔍 줄 해석
  • HTTP_X_FORWARDED_FOR를 먼저 봅니다 — 프록시·로드밸런서를 거치면 REMOTE_ADDR가 프록시 IP가 되기 때문입니다.
  • 그 헤더는 클라이언트, 프록시1, 프록시2 형태의 체인이라 explode(',')[0]으로 첫 IP만 씁니다.
  • substr(..., 0, 45) — IPv6 최대 길이가 45자. 컬럼 크기에 맞춰 자릅니다.
  • @mysqli_prepare가 실패하면 ensureOpsSchema()를 부르고 다시 시도합니다. 테이블이 아직 없는 첫 실행에서도 알아서 복구됩니다.
  • 로깅 실패가 로그인 자체를 막으면 안 되므로 @로 에러를 삼킵니다. 부가 기능이 본 기능을 죽이지 않게 하는 패턴입니다.

CODE 6KIS 토큰 발급과 캐싱

외부 API는 호출 횟수 자체가 자원입니다. 이 파일이 그걸 아끼는 법을 보여줍니다.

🔍 줄 해석
  • 왜 캐싱하나: 요청마다 새 토큰을 발급받다가 발급 제한에 걸렸던 적이 있습니다(1편 트러블슈팅 사례 5).
  • 캐시 파일에 expire_at을 같이 저장하고, 아직 안 지났으면 네트워크를 아예 타지 않고 재사용합니다.
  • 23시간으로 잡은 이유: 실제 만료는 24시간인데, 딱 맞추면 "쓰려는 순간 막 만료된" 경우가 생깁니다. 여유(safety margin)를 둔 것입니다.
  • openapivts...:29443 — vts = 모의투자 도메인입니다. 실전 도메인과 주소가 다릅니다.
  • 발급 실패 시 throw — 토큰 없이 뒤 로직을 진행해도 어차피 다 실패하므로 여기서 끊습니다.
  • ⚠️ 캐시 파일 token_cache.json이 노출되면 남이 우리 토큰을 그대로 씁니다. 그래서 config/.htaccess가 폴더째 막고 있습니다(CODE 2).

CODE 7시세 API 공통 헬퍼

KIS 시세 API 6종이 전부 이 함수 하나를 거칩니다. 같은 코드를 여섯 번 쓰지 않으려고 만든 것입니다.

🔍 줄 해석
  • 매개변수가 $path, $trId, $params 셋뿐입니다. KIS API는 주소·tr_id·파라미터만 다르고 나머지(헤더·인증·타임아웃)는 전부 같기 때문에 그 공통부를 여기 모았습니다.
  • tr_id가 "무슨 기능을 부를지"를 고르는 스위치입니다. FHKST01010100=현재가, FHKST01010200=호가, FHKST03010100=일봉.
  • CURLOPT_TIMEOUT => 10 — 응답이 10초를 넘으면 포기합니다. 없으면 한 종목이 멈추면 전체가 멈춥니다.
  • EGW00201 재시도가 핵심: KIS의 "초당 호출 제한 초과" 에러입니다. 0.7초 쉬고 자기 자신을 다시 호출(재귀)합니다.
  • $retryCount < 3 — 재귀에 반드시 탈출 조건이 필요합니다. 없으면 서버가 계속 거부할 때 무한 재귀로 죽습니다.

CODE 8일봉 API — 100행의 벽

"3개월/1년/2년 탭"이 실제로 동작하게 만든 함수입니다. 실제로 호출해보고 알아낸 제약이 설계를 결정했습니다.

🔍 줄 해석
  • FID_ORG_ADJ_PRC = '0' — 수정주가를 켭니다. 액면분할이 있었던 종목은 이걸 안 켜면 과거 가격이 계단처럼 튑니다.
  • rt_cd !== '0'이면 빈 배열 — KIS는 실패해도 HTTP 200을 주므로 본문의 결과코드를 봐야 합니다.
  • strlen($d) !== 8 · $close <= 0 — 휴장일이나 미체결 행이 빈 값으로 섞여 옵니다. 그대로 저장하면 차트에 0원짜리 봉이 찍힙니다.
  • 마지막 usort — KIS는 최신 날짜부터 역순으로 줍니다. 차트는 시간 오름차순이어야 하므로 뒤집습니다.
🔑 실호출로 알아낸 제약 — 한 번 호출에 정확히 100행이고, 요청 구간을 아무리 길게 줘도 끝 날짜 기준 최근 100행만 줍니다. 그래서 2년치를 받으려면 끝 날짜를 뒤로 밀어가며 5번 반복해야 합니다. 그 반복이 cron/backfill_daily.php입니다(CODE 24).
문서만 읽고 "구간을 넓게 주면 되겠지"라고 짰다면 조용히 100행만 받고 끝났을 겁니다. 외부 API는 실제로 불러봐야 압니다.

CODE 9실주문과 해시키

지금 사이트의 매매는 우리 DB에서만 일어나지만, KIS 모의투자 계좌로 진짜 주문을 내는 경로도 만들어져 있습니다.

🔍 줄 해석
  • 주문 본문을 먼저 KIS에 보내 서명값(HASH)을 받아옵니다. 그 값을 실제 주문 요청의 헤더에 실어 보냅니다.
  • 목적은 위변조 방지 — 중간에서 수량이나 종목이 바뀌면 해시가 안 맞아 거부됩니다.
🔍 줄 해석
  • $trId = ($orderType === 'buy') ? 'VTTC0802U' : 'VTTC0801U' — VT로 시작하면 모의투자입니다. 실전은 다른 코드입니다.
  • ORD_DVSN = "01" = 시장가. 그래서 ORD_UNPR(주문단가)는 "0"입니다 — 시장가는 가격을 지정하지 않습니다.
  • 숫자를 문자열로 보냅니다((string)$quantity). KIS 규격이 문자열을 요구합니다.
  • 재시도 판단이 정교합니다: ⓐ 네트워크 오류 ⓑ 초당 제한(EGW00201) ⓒ 응답 파싱 실패 — 이 셋만 재시도하고, "잔고 부족" 같은 논리적 실패는 재시도하지 않습니다. 재시도해봐야 같은 답이니까요.
  • 주문은 최대 2회만 재시도합니다(시세 조회는 3회). 돈이 움직이는 요청은 중복 체결 위험이 있어 더 보수적으로 잡았습니다.

CODE 10오픈 리다이렉트 방어

"로그인하면 원래 보던 페이지로 돌려보내기"는 편의 기능인데, 잘못 만들면 피싱 도구가 됩니다.

🔍 줄 해석
  • requireUserLogin()은 서버측 게이트입니다. 화면에서 메뉴를 숨기는 것만으론 주소를 직접 치면 들어가집니다.
  • 돌아갈 주소를 ?next=에 담아 로그인 페이지로 보냅니다.
  • 위험: 그 값을 그대로 믿고 이동하면 공격자가 ?next=//evil.com을 심어 우리 사이트를 거쳐 피싱 사이트로 보낼 수 있습니다. 사용자는 우리 도메인에서 시작했으니 의심하지 않습니다.
  • safeNext()의 정규식 ^[A-Za-z0-9_]+\.php(\?...)?$ — 같은 폴더의 .php 파일명만 통과시킵니다. //, http://, ../가 전부 걸러집니다.
  • 허용 목록(whitelist) 방식입니다 — "나쁜 걸 막는" 대신 "좋은 것만 통과". 새로운 공격 패턴이 나와도 안전합니다.

🔍 줄 해석

CODE 12매수 — 트랜잭션의 핵심

이 프로젝트에서 가장 중요한 함수입니다. 돈이 움직이는 모든 규칙이 여기 있습니다.

🔍 줄 해석
  • 진입부 2차 검증 — 화면에서 이미 걸렀는데도 다시 봅니다. 브라우저에서 오는 값은 전부 조작 가능하기 때문입니다. 실제로 음수 수량 버그가 있었습니다.
  • mysqli_begin_transaction() — 여기서부터 commit까지는 전부 성공하거나 전부 취소됩니다.
  • FOR UPDATE가 이 함수의 심장입니다. 잔고 행을 잠급니다. 이게 없으면:
    [FOR UPDATE 없을 때 — 잔고 100만원] 요청A: 잔고 읽음(100만) ──┐ 요청B: 잔고 읽음(100만) ──┤ 둘 다 "충분하다"고 판단 요청A: 100만 차감 → 0 ─┘ 요청B: 100만 차감 → -100만 ⚠️ 잔고가 마이너스! [FOR UPDATE 있을 때] 요청A: 잔고 읽고 잠금 → 차감 → commit(잠금 해제) 요청B: (A가 끝날 때까지 대기) → 잔고 0 읽음 → "부족합니다" ✅
  • 순서가 의도적입니다: 잔고 확인 → 차감 → 보유 반영 → 주문 기록. 가장 실패 가능성이 높은 것(잔고)을 맨 앞에 둬서 헛일을 줄입니다.
  • 평균단가 재계산: (기존수량×기존평단 + 신규수량×신규가) ÷ 총수량. 이걸 틀리면 수익률이 전부 틀어집니다.
  • 보유 행도 FOR UPDATE로 잠급니다 — 같은 종목을 동시에 사면 평단이 꼬입니다.
  • catch에서 rollback() 후 예외를 다시 던집니다(throw $e). 되돌리는 건 여기 책임이고, 사용자에게 뭐라고 말할지는 호출한 쪽 책임이기 때문입니다.

CODE 13매도

🔍 줄 해석
  • 구조는 매수와 거울처럼 같습니다. 다른 점 세 가지만 보면 됩니다.
  • ① 검증 대상이 다름 — 매수는 "돈이 충분한가", 매도는 "주식이 충분한가".
  • ② 0이 되면 행을 삭제 — quantity=0인 행을 남기지 않고 DELETE합니다. 보유 목록이 깔끔해집니다.
    다만 부작용이 있습니다: 전량 매도하면 그 종목의 평단 기록이 사라집니다. 그래서 과거 수익률은 따로 복원해야 합니다(CODE 14).
  • ③ 평단을 갱신하지 않음 — 매도는 수량만 줄입니다. 평단은 "얼마에 샀나"이므로 파는 행위로 바뀌지 않습니다. 초보가 자주 틀리는 부분입니다.
  • 주석에 남아 있듯, 음수 수량 매도는 보유수량을 늘리고 현금을 깎는 역버그가 됩니다. 그래서 진입부 검증이 필수입니다.

CODE 14과거 평단 복원 — 없는 데이터를 되살리기

"3개월 전에 판 그 주식, 몇 % 먹었지?"에 답하는 함수입니다. 그 답은 DB에 없습니다.

문제: holdings.avg_price는 '지금' 평단이고, 전량 매도하면 행 자체가 사라집니다. 그래서 "그때 그 시점의 평단"은 DB 어디에도 없습니다.
🔍 줄 해석
  • 해법 = 재생(replay). orders 테이블에는 모든 주문이 시간순으로 남아 있습니다. 그걸 처음부터 다시 훑으면서 processBuy와 같은 방식으로 평단을 다시 쌓습니다.
  • ORDER BY o.created_at ASC, o.id ASC — 반드시 오래된 순으로 읽어야 재생이 성립합니다. id를 2차 정렬로 둔 이유는 같은 초에 들어온 주문의 순서를 확정하기 위해서입니다.
  • $book[종목] = ['qty'=>보유수량, 'cost'=>매입원가 합계] — 이게 재생용 장부입니다.
  • 매수 행: 장부에 더하고, 표시 수익률은 "매수가 대비 현재가"로 냅니다. 아직 판 게 아니라 손익이 확정되지 않았기 때문입니다(rate_basis='current').
  • 매도 행: 그 시점 평단 = cost ÷ qty로 구하고, 실현수익률을 계산합니다(rate_basis='realized'). 두 종류를 구분해서 표시하는 게 정직한 UI입니다.
  • min($qty, $book[$code]['qty']) — 데이터가 꼬여 보유보다 많이 파는 기록이 있어도 음수로 내려가지 않게 방어합니다.
  • 마지막에 array_reverse로 최신이 위로 오게 뒤집고 N건만 자릅니다. 재생은 오래된 순이어야 하지만 보여주는 건 최신 순이라, 순서를 두 번 뒤집는 겁니다.
배울 점 — "그 값을 저장해두지 않았다"고 해서 포기할 필요가 없습니다. 변경 이력이 남아 있으면 어느 시점의 상태든 재구성할 수 있습니다. (이벤트 소싱과 같은 발상입니다)

CODE 15스키마 자동 보강 — MySQL엔 없는 문법

🔍 줄 해석
  • static $done — 한 요청에서 여러 번 불려도 확인은 한 번만. 페이지마다 information_schema 조회를 반복하면 낭비입니다.

CODE 16차트 규격표 — 한 눈에 보이는 설계

차트의 모든 동작이 이 표 하나에서 결정됩니다.

🔍 줄 해석
  • src = 어느 테이블에서 읽을지, bucket = 봉 하나가 몇 초짜리인지, days = 며칠 전부터 볼지.
  • 기간이 길수록 봉이 굵습니다. 그래서 어느 탭을 눌러도 캔들이 수백 개로 유지됩니다 — "2년 보기"가 "오늘 보기"보다 무겁지 않은 이유입니다.
  • 1M이 daily인 게 2026-08-07 수정 사항입니다. 원래 30분봉이었는데, 분 데이터는 수집 시작일(2026-07-20)부터만 있어서 "1개월"을 눌러도 18일치만 나왔습니다. 일봉은 2024년부터 다 있는데 안 쓰고 있었던 겁니다.
  • 5Y는 버튼에서 뺐지만 표에는 남겨뒀습니다 — 옛 링크나 북마크가 죽지 않게 하려는 것입니다. 나중에 5년치를 백필하면 버튼만 되살리면 됩니다.
  • $map[$key] ?? $map['1D'] — 모르는 값이 오면 에러 대신 1D로 떨어집니다. 외부 입력에 대해 "안전한 기본값"을 두는 패턴입니다.
⚠️ 이 표를 고치면 반드시 같이 고쳐야 하는 곳이 2군데 더 있습니다 (프론트, CODE 20 참고)
① isDailyRange() — 빠뜨리면 시:분 축이 켜진 채라 모든 봉이 00:00으로 찍힙니다.
② RANGE_BUCKET — 일봉 구간을 남겨두면 실시간 캔들(숫자)과 일봉(문자열)이 섞여 봉이 엉뚱한 자리에 떨어집니다.

CODE 17분봉 조회 — 자가 치유

수집기가 며칠 꺼져 있었어도 차트에 구멍이 안 나게 만드는 설계입니다.

🔍 줄 해석
  • getCandleData는 교통정리만 합니다 — 규격표를 보고 일봉이면 일봉 함수로, 분봉이면 분봉 함수로 보냅니다. 이렇게 나눠두면 각 함수가 한 가지 일만 하게 됩니다.
  • ①번 쿼리: FROM_UNIXTIME(FLOOR(UNIX_TIMESTAMP(ts) / ?) * ?) — 이게 버킷 만들기입니다. 300으로 나눠 내림하고 다시 300을 곱하면 5분 단위로 뭉갠 시각이 나옵니다. 같은 값이 된 행들을 GROUP BY로 묶으면 5분봉이 됩니다.
  • 시가는 GROUP_CONCAT(... ORDER BY ts ASC)의 첫 값, 종가는 ORDER BY ts DESC의 첫 값. MySQL엔 "그룹의 첫 값"을 뽑는 집계함수가 없어서 쓰는 관용구입니다.
  • ②번이 자가 치유의 핵심: 분봉 테이블이 어디까지 있는지(MAX(ts)) 확인하고, 그 뒤 구간만 원시 로그로 즉석 집계합니다.
  • created_at > ? — 경계를 초과(>)로 잡습니다. >=였다면 마지막 분이 양쪽에 다 들어가 중복 캔들이 생깁니다. 부등호 하나의 차이입니다.
  • 마지막 병합: $merged[$r['time']] = $r — 같은 시각이면 나중 것이 덮어씁니다. 배열 순서상 원시 로그(더 최신)가 뒤에 오므로 그쪽이 이깁니다.
  • ksort로 시각 순 정렬 후 array_values로 키를 버리고 순서 배열로 만듭니다. JSON으로 나갈 때 객체가 아니라 배열이 되게 하려는 것입니다.
실측으로 본 자가 치유의 대가
분봉이 하루 멈춰 있을 때 1주 탭이 4.3초까지 느려졌다가, 정상 상태에서는 46ms였습니다. 즉석 집계 구간이 길수록 느려지는 것입니다.
👉 차트가 갑자기 느려지면 "수집기가 죽었나?"를 먼저 의심하면 됩니다. 성능이 곧 상태 표시등 역할을 합니다.

  • ensureCandle1dTable()을 먼저 부릅니다 — 테이블이 없어도 알아서 만들어집니다.
🔍 줄 해석

검증 방법 — 이런 버그는 "잘 되는 것처럼 보입니다". 그래서 눈으로 확인하지 않고, 분봉 41,638개를 원본 틱과 전수 대조해 시가·고가·저가·종가·건수 불일치 0을 확인했습니다.

🔍 줄 해석

프론트 — 실시간 캔들 갱신

🔍 줄 해석
  • const bucketSec = RANGE_BUCKET[currentRange]; if (!bucketSec) return; — 일봉 구간이면 아무것도 안 합니다. RANGE_BUCKET에 일봉 항목이 없는 게 곧 "실시간 갱신 안 함"이라는 뜻입니다. 없음(undefined)을 스위치로 쓰는 방식입니다.
  • Math.floor((timestamp + KST_OFFSET) / bucketSec) * bucketSec — 서버와 같은 방식으로 버킷을 계산합니다. KST_OFFSET이 바로 9시간 버그의 해결책입니다.
  • last.time === slot이면 같은 봉 갱신(고가·저가·종가만), 새 칸이면 새 봉 추가.
  • else { return; } — 이미 지나간 칸의 뒤늦은 체결은 무시합니다. 과거 봉을 건드리면 차트가 튑니다.

CODE 211분봉 누적기 — 전체

99줄짜리 파일 하나가 "저장은 줄이고 정확도는 안 줄인다"를 실현합니다. 순수 함수뿐이라 웹소켓 없이 테스트할 수 있습니다.

🔍 줄 해석 — minuteKeyKst
  • 로컬 시간대를 아예 안 씁니다. new Date(ms + 9시간)으로 직접 9시간을 더한 뒤 getUTCHours() 같은 UTC 계열로 읽습니다.
  • 왜? getHours()는 실행하는 PC의 시간대를 따릅니다. 형 PC(KST)와 서버(UTC)에서 답이 달라집니다. 이 방식은 어디서 돌려도 같은 값이 나옵니다.
  • padStart(2,'0')으로 자릿수를 맞춰 '2026-08-07 09:05:00' 형태를 만듭니다. DB의 DATETIME과 같은 모양이라 그대로 넣을 수 있습니다.
🔍 줄 해석 — accumulateCandle
  • 이상치 방어가 맨 앞: !Number.isFinite(price) || price <= 0. KIS가 드물게 0이나 NaN을 흘리는데, 그게 low_p로 굳으면 차트가 바닥까지 찍힙니다. 들어오는 즉시 버립니다.
  • 키가 종목코드 + '|' + 분입니다. 종목이 섞이지 않고, 분이 바뀌면 자동으로 새 캔들이 됩니다.
  • 첫 체결이 시가: if (!c)일 때만 o: price를 설정합니다. 이후엔 절대 안 건드립니다.
  • 고가·저가는 비교해서 갱신, 종가는 매번 덮어씀 — 마지막에 덮인 값이 곧 그 분의 마지막 체결가가 됩니다. 별도 처리가 필요 없습니다.
  • if (vol > c.vol) c.vol = vol — 누적거래량은 단조 증가해야 합니다. 되돌아가는 값은 패킷 순서가 뒤바뀐 것이므로 무시합니다.
  • dVol += q가 중요합니다 — 건별 체결량을 그대로 더합니다. 원시 로그로 계산할 때처럼 MAX-MIN 뺄셈을 할 필요가 없어서 분 경계 오차가 없습니다.
🔍 줄 해석 — flushCandles
  • if (c.dTicks > 0) — 변화가 있었던 것만 내보냅니다. 조용한 종목은 DB를 안 건드립니다.
  • 내보낸 뒤 dVol = 0; dTicks = 0; — 델타 리셋. 이게 없으면 DB에서 ticks = ticks + VALUES(ticks)로 더할 때 같은 값을 반복해서 더합니다.
  • if (c.ts !== currentKey) store.delete(id) — 지나간 분은 Map에서 제거합니다. 안 하면 하루 종일 캔들이 쌓여 메모리 누수가 됩니다. 진행 중인 분은 남겨둬야 고가·저가 누적이 이어집니다.
왜 이 파일을 따로 뗐나 — index.js는 웹소켓 접속·재접속·구독 관리까지 하는 큰 파일입니다. 거기 섞으면 테스트를 못 합니다. 순수 함수로 떼어낸 덕분에 test_candles.js가 웹소켓 없이 39개 회귀 테스트(타임존·OHLC·이상치·델타 중복·메모리 정리·종목 독립·1만 건 부하)를 돌립니다. 돈이 걸린 숫자라 회귀 테스트가 꼭 필요했습니다.

🔍 줄 해석

CODE 24cron 3종

24-1. 분봉 보수 집계 — INSERT IGNORE 한 단어의 설계

🔍 줄 해석
  • 역할 분담이 이 파일의 전부입니다. 주 경로는 수집기(정밀), 이 파일은 보수 경로(수집기가 꺼져 있던 구간을 뒤늦게 메움).
  • INSERT IGNORE — 이미 있는 분은 절대 안 건드립니다. 수집기가 만든 정밀 분봉을, 10초 간격으로 듬성한 원시 로그 집계로 덮어쓰면 손해이기 때문입니다.
    👉 "정밀한 쪽이 이긴다"는 규칙을 SQL 문법 한 단어로 못박은 것입니다. 코드로 조건 분기를 하지 않아도 됩니다.
  • vol_delta = GREATEST(MAX(volume) - MIN(volume), 0) — 원시 로그엔 누적거래량만 있고 건별 체결량이 없어서 뺄셈으로 근사합니다. 수집기가 훨씬 정확한 이유입니다. 이 근사치라는 점도 "안 건드린다" 규칙의 근거입니다.
  • 진행 중인 분은 항상 제외합니다(< 현재 분). 아직 체결이 더 들어올 수 있는데 굳혀버리면 틀린 값이 남습니다.
  • 구간 기준을 전부 DB의 NOW()로 잡습니다 — PHP date()면 9시간 어긋납니다.
  • 인자를 3가지로 받습니다: 분 수 / 날짜 / --all. 평소엔 5분마다 최근 30분, 최초 1회는 전 구간이라는 두 용도를 한 파일로 처리합니다.

24-2. 일봉 백필 — 100행의 벽을 넘는 반복

🔍 줄 해석
  • while(true) 루프가 이 파일의 존재 이유입니다. KIS가 한 번에 100행만 주므로, 끝 날짜를 뒤로 밀어가며 반복 호출합니다.
  • $to = date('Ymd', strtotime($oldest . ' -1 day')) — 방금 받은 것 중 가장 오래된 날의 하루 전을 다음 끝 날짜로 삼습니다. 이렇게 과거로 걸어갑니다.
  • 탈출 조건이 4개입니다:
    ① 데이터가 안 오면(상장 전) ② 목표 기간 도달 ③ 100행 미만이면 = 그 종목의 상장 시작까지 왔다는 뜻 ④ $guard >= 25 무한루프 방지.
    👉 외부 API를 반복 호출하는 루프에는 반드시 가드가 필요합니다. API가 예상 밖 응답을 주면 영원히 돌 수 있습니다.
  • usleep(300000) = 0.3초 간격 — 초당 호출 제한 회피. 초과분은 kisQuotationGet이 재시도합니다(CODE 7). 방어가 두 겹입니다.
  • ON DUPLICATE KEY UPDATE로 덮어씁니다(분봉과 반대!). KIS 값이 항상 정답이고, 수정주가는 시간이 지나면 과거 값 자체가 바뀌므로 갱신되는 게 맞습니다.
  • 인자 없이 돌리면 최근 100영업일만 — 이게 매일 스케줄러용입니다. 이걸 안 돌리면 차트 날짜가 매일 하루씩 밀립니다(실제로 겪은 증상).
  • 대상 = 기본종목 ∪ 순위종목 ∪ 관심종목. PHP의 + 배열 합집합은 키 중복 시 왼쪽 우선이라 중복 제거가 자동입니다.

24-3. 원시 로그 정리 — 지우기 전에 확인

🔍 줄 해석
  • 🔒 안전장치가 이 스크립트에서 가장 중요합니다. 그날 분봉 커버리지가 90% 미만이면 그날은 건너뜁니다. 분봉 없이 원본을 지우면 그 구간은 영영 복구 불가입니다.
  • 커버리지 = 그날 분봉이 있는 종목 수 ÷ 그날 로그를 남긴 종목 수. "행 수"가 아니라 "종목 수"로 재는 게 포인트입니다 — 한 종목만 잔뜩 있어도 커버리지가 높아 보이면 안 되니까요.
  • --dry 드라이런 — 되돌릴 수 없는 작업은 미리보기부터 만듭니다. 실제로 이 옵션으로 "2,240,497행(86%) 삭제 예정"을 먼저 확인했습니다.
  • 청크 삭제(LIMIT 50000 + usleep) — 통째로 DELETE하면 락이 오래 걸려 수집기가 밀립니다. 5만 행씩 끊고 0.2초씩 쉬어 사이사이 INSERT할 틈을 줍니다.
  • 마지막 OPTIMIZE TABLE은 안내만 하고 실행하지 않습니다. InnoDB는 DELETE만으론 디스크가 안 줄지만, 이 명령은 테이블을 통째로 다시 써서 장중에 돌리면 수집이 멈춥니다.
    👉 위험한 일은 자동으로 하지 않고 사람에게 넘기는 판단입니다.

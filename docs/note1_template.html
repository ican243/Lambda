1-2. 다섯 가지 핵심 설계 결정

이 프로젝트를 이해한다는 건 사실 이 다섯 개의 "왜"를 아는 것입니다. 나머지는 곁가지입니다.

① 화면은 DB를 기다리지 않는다

실시간 체결이 오면 브라우저로 먼저 쏘고, 그 다음에 DB에 저장합니다. 순서를 반대로 하면 DB가 느려질 때 화면까지 같이 멎습니다. 원격 공용 DB를 쓰는 지금은 더 중요해졌습니다.

stock-ws/index.jshandleTrade()
② 저장은 줄이고, 정확도는 안 줄인다 스로틀 + 분봉

체결은 초당 수십 건씩 옵니다. 전부 저장하면 DB가 터집니다. 그래서 원시 기록은 10초에 1건만 저장합니다. 그런데 그러면 그 10초 사이의 최고가·최저가가 사라집니다.
→ 해결: 모든 체결은 메모리에서 1분봉으로 누적하고, DB에는 10초마다 한 번만 씁니다. 저장량은 줄고 OHLC 정밀도는 원본 그대로입니다.

stock-ws/candles.jsaccumulateCandle()
③ 어느 기간을 눌러도 캔들 수는 수백 개 해상도 분리

1분봉으로 1년을 그리면 캔들이 9만 개, JSON이 수 MB가 됩니다. 브라우저가 멈춥니다.
→ 해결: 기간마다 봉의 굵기를 바꿉니다. 1일=1분봉, 1주=5분봉, 1개월 이상=일봉. 그래서 "1년 보기"가 "오늘 보기"보다 무거워지지 않습니다.

user/func.phpchartRangeSpec()
④ 시각은 항상 DB에게 물어본다 타임존

원격 DB 서버의 시계는 UTC인데 우리 데이터·로직은 전부 KST(한국시간)입니다. PHP는 또 UTC로 돕니다. 세 개가 어긋나면 "오늘"이 통째로 사라집니다.
→ 규칙: 날짜·시각 계산은 PHP의 date()가 아니라 DB의 NOW()/CURDATE()로 합니다. 커넥션마다 SET time_zone='+09:00'도 겁니다.

이 프로젝트에서 가장 많이 터진 버그 유형
⑤ 스키마는 코드가 알아서 만든다 ensure*()

새 기능을 붙일 때 "형이 SQL을 직접 돌려야 함"이 되면, 다음 세션에서 잊어버리고 "왜 안 되지"로 시간을 버립니다.
→ 규칙: 테이블·컬럼이 필요하면 코드가 CREATE TABLE IF NOT EXISTS / information_schema 확인 후 ALTER를 스스로 합니다. ensureOpsSchema, ensurePostsTable, ensureCandle1dTable, ensureAutoTradeSchema, ensureAdminSchema 5개가 그 역할입니다.

SECTION 2웹이 돌아가는 원리

코드를 읽기 전에 이것부터. "이 코드가 어디서 실행되는가"를 모르면 모든 게 헷갈립니다.

2-1. 서버와 브라우저는 다른 컴퓨터다

[브라우저 = 형 PC] [서버 = Apache + PHP] │ │ │ ① "stock_detail.php 줘" ─────────────▶ │ │ │ ② PHP가 실행됨 │ │ - DB 조회 │ │ - HTML 문자열 조립 │ ③ 완성된 HTML ◀─────────────────────── │ │ │ │ ④ 브라우저가 HTML을 그림 │ │ 이때부터 JS가 실행됨 │ (PHP는 이미 끝났음) │ │ │ ⑤ JS가 fetch()로 추가 요청 ─────────────▶ │ ⑥ get_stock_chart.php 실행 │ (화면 안 바뀜) │ JSON만 응답 │ ⑦ JSON 받아서 화면 일부만 갱신 ◀────────── │
핵심 여기서 헷갈리면 다 헷갈립니다
PHP는 HTML을 만들어 보내면 그 순간 끝납니다. 브라우저에서 버튼을 눌러도 그 PHP는 이미 죽었습니다. 그래서 화면을 바꾸려면 ⓐ JS가 직접 바꾸거나 ⓑ 새 요청을 보내 PHP를 다시 실행해야 합니다.

SECTION 3용어사전 — 75개

이 프로젝트를 읽다 막히는 단어는 거의 다 여기 있습니다. 6개 분야로 묶었습니다.

A. 웹 기본 (12개)

HTTP HyperText Transfer Protocol
브라우저와 서버가 대화하는 약속. "이거 줘(GET)", "이거 처리해줘(POST)" 같은 요청과, 숫자 코드로 된 응답(200 성공, 403 금지, 404 없음, 500 서버오류)으로 이뤄집니다.
GET / POST
GET은 주소창에 다 보이는 요청(조회용), POST는 본문에 숨겨 보내는 요청(변경용). 매수 주문 같은 건 반드시 POST여야 합니다 — GET이면 링크 한 번에 주문이 나갑니다.
쿼리스트링 query string
주소 뒤 ?stock_code=005930&range=1D 부분. 서버에서 $_GET['stock_code']로 읽습니다.
JSON
데이터를 주고받는 문자열 형식. {"price":235000} 처럼 생겼습니다. PHP는 json_encode()로 만들고, JS는 res.json()으로 읽습니다.
API / 엔드포인트
"프로그램끼리 대화하는 창구". 우리 user/get_quote.php는 우리가 만든 API고, KIS의 inquire-price는 남이 만든 API입니다.
REST
"필요할 때 한 번 물어보고 답 받고 끝"인 통신 방식. 새로고침해야 새 값이 옵니다. 반대는 웹소켓.
웹소켓 WebSocket
한 번 연결해두면 서버가 먼저 말을 걸 수 있는 통로. 시세처럼 계속 바뀌는 데이터에 씁니다. 주소가 http가 아니라 ws로 시작합니다.
fetch()
JS에서 화면 새로고침 없이 서버에 요청하는 함수. 우리 차트 기간 탭이 이걸로 동작합니다.
세션 session
서버가 "이 브라우저는 3번 유저"라고 기억하는 것. 브라우저엔 열쇠(쿠키)만 주고 내용은 서버에 둡니다. 그래서 사용자가 못 고칩니다.
쿠키 cookie
브라우저가 들고 다니는 작은 쪽지. 우리는 세션 ID만 담습니다.
리다이렉트 redirect
"거기 말고 저기로 가"라는 응답(302). header('Location: ...'). 반드시 뒤에 exit;를 붙여야 합니다 — 안 붙이면 아래 코드가 계속 실행됩니다.
.htaccess
Apache에게 주는 폴더별 지시서. 우리는 config/와 stock-ws/를 웹에서 아예 못 열게 막는 데 씁니다.

B. 언어·화면 (13개)

변수 / 배열 / 연관배열
PHP 변수는 $로 시작. 배열은 값의 줄, 연관배열은 ['price' => 235000]처럼 이름표가 붙은 배열. DB 한 행이 보통 연관배열로 옵니다.
함수 function
이름 붙인 코드 묶음. 같은 걸 여러 곳에서 쓰려고 만듭니다. processBuy()처럼.
require_once
다른 PHP 파일을 서버 안에서 불러오기. 웹으로 접근 못 하게 막아도 이건 잘 됩니다(그래서 config/.htaccess가 안전합니다).
예외 Exception
"여기서 더 진행하면 안 됨"을 알리는 장치. throw로 던지고 try/catch로 받습니다. 우리 매수/매도가 이걸로 롤백을 판단합니다.
삼항 연산자
조건 ? A : B — 짧은 if. ??는 "왼쪽이 없으면 오른쪽"(null 병합).
DOM
브라우저가 HTML을 다루는 구조. document.getElementById('chart')로 특정 요소를 집어 옵니다.
이벤트 event
클릭·입력 같은 사건. addEventListener('click', ...)로 "이 일이 생기면 이걸 해라"를 등록합니다.
이벤트 위임 delegation
버튼 6개에 각각 리스너를 다는 대신 부모에 하나만 달고 e.target.closest()로 누가 눌렸는지 찾는 방식. 우리 기간 탭이 이걸 씁니다.
async / await
"오래 걸리는 일(네트워크·DB)을 기다리되, 그동안 다른 일은 막지 않는다". await 앞의 함수는 async여야 합니다.
Promise
"나중에 값이 올 것"을 담은 상자. await가 그 상자를 열어줍니다.
Map
JS의 키-값 저장소. 객체와 비슷하지만 키 종류가 자유롭고 크기를 .size로 바로 압니다. 우리 분봉 누적기가 Map<"종목|분", 캔들>을 씁니다.
setInterval
"N밀리초마다 반복 실행". 분봉 저장(10초), 요약 로그(30초), 워치독(30초)에 씁니다.
CSS 변수
--accent:#4a90ff처럼 색을 이름으로 정의해두고 var(--accent)로 쓰는 것. 색 하나만 고치면 사이트 전체가 바뀝니다.

C. 데이터베이스 (15개)

테이블 / 행 / 컬럼
엑셀 시트 = 테이블, 가로줄 = 행(row), 세로칸 = 컬럼(column).
기본키 PRIMARY KEY
행을 유일하게 구분하는 값. 중복이 불가능합니다. stock_candles_1m은 (종목코드, 시각) 두 개를 묶어 기본키로 씁니다 — "같은 종목의 같은 분은 하나뿐"이라는 규칙이 여기서 강제됩니다.
인덱스 INDEX
책 뒤 찾아보기. 조회는 빨라지고 저장은 조금 느려지며 용량을 먹습니다. 우리 stock_logs는 인덱스가 데이터보다 큽니다(175MB vs 168MB).
외래키 FOREIGN KEY
"이 값은 저 테이블에 반드시 존재해야 함". ON DELETE CASCADE를 붙이면 부모가 지워질 때 자식도 같이 지워집니다.
JOIN
두 테이블을 이어 붙여 조회. INNER JOIN은 양쪽 다 있는 것만, LEFT JOIN은 왼쪽 건 다 두고 오른쪽은 없으면 NULL.
트랜잭션 transaction
"전부 성공하거나 전부 취소". 돈 계산의 핵심입니다. begin_transaction → 여러 쿼리 → commit, 문제가 생기면 rollback.
FOR UPDATE 행 잠금
트랜잭션 안에서 읽은 행을 다른 요청이 못 건드리게 잠급니다. 이게 없으면 잔고 100만원으로 동시에 두 번 매수해서 잔고가 마이너스가 될 수 있습니다.
UPSERT INSERT ... ON DUPLICATE KEY UPDATE
"없으면 넣고, 있으면 고쳐라"를 한 방에. 분봉 저장의 핵심입니다.
INSERT IGNORE
"이미 있으면 조용히 넘어가라". aggregate_candles.php가 이걸 써서, 수집기가 만든 정밀 분봉을 절대 덮어쓰지 않습니다.
prepared statement
SQL 틀을 먼저 보내고 값을 따로 보내는 방식. 값이 SQL 문법으로 해석될 수 없어 SQL 인젝션이 원천 차단됩니다. mysqli_prepare + bind_param.
바인드 타입 "isd s"
bind_param("isid", ...)의 문자열. i=정수, s=문자열, d=실수, b=바이너리. 순서와 개수가 값과 정확히 맞아야 합니다.
GROUP BY / 집계함수
같은 값끼리 묶어 MAX·MIN·SUM·COUNT를 냅니다. 분봉 만들기가 바로 "1분 단위로 GROUP BY 해서 MAX=고가, MIN=저가".
GROUP_CONCAT 관용구
MySQL엔 "그룹의 첫 값"을 뽑는 집계함수가 없습니다. 그래서 SUBSTRING_INDEX(GROUP_CONCAT(price ORDER BY id ASC), ',', 1)로 시가를 뽑는 관용구를 씁니다. ⚠️ 기본 길이 제한이 1024바이트라 넘으면 조용히 잘립니다 → SET SESSION group_concat_max_len 필수.
컬레이션 collation
문자 비교 규칙. 우리 DB엔 3종이 섞여 있어서, 맞추지 않으면 JOIN이 "illegal mix of collations"로 깨집니다. 새 테이블은 utf8mb3_unicode_ci로 맞춥니다.
OPTIMIZE TABLE
InnoDB는 DELETE만으로는 디스크가 안 줄어듭니다(빈 공간을 재사용할 뿐). 실제로 반납하려면 이 명령이 필요한데, 테이블을 통째로 다시 써서 장중에 돌리면 수집이 멈춥니다.

D. 시계열·차트 (14개) 이번 판 신설

틱 tick
체결 1건. "누가 몇 주를 얼마에 샀다"는 한 사건. 우리 stock_logs가 이 원본입니다.
캔들 / OHLC
일정 시간 동안의 가격을 막대 하나로 요약한 것. Open(시가·첫 가격), High(고가·최고), Low(저가·최저), Close(종가·마지막 가격).
해상도 resolution
봉 하나가 담는 시간. 1분봉·5분봉·일봉. 기간이 길수록 봉을 굵게 해야 캔들 개수가 안 터집니다.
버킷 bucket
시간을 일정 간격으로 나눈 칸. FLOOR(UNIX_TIMESTAMP(ts)/300)*300 = 5분 칸으로 내림. 같은 칸에 든 값들을 묶으면 5분봉이 됩니다.
누적거래량 acml_vol
그날 0시부터 지금까지 합계. 계속 증가하다 다음 날 0으로 리셋됩니다. 그래서 "이 1분에 얼마나 거래됐나"를 알려면 뺄셈이 필요합니다.
델타 delta
"지난번 이후 늘어난 몫". 진행 중인 분을 10초마다 여러 번 저장할 때, 총합을 매번 보내면 DB에서 더할 때 중복 가산됩니다. 그래서 늘어난 몫만 보내고 0으로 리셋합니다.
스로틀 throttle
"아무리 많이 와도 N초에 한 번만 처리". 우리는 stock_logs 10초, stock_latest 1초로 겁니다.
백필 backfill
과거 데이터를 뒤늦게 채워 넣기. 우리는 KIS 일봉 API로 2년치를 백필했습니다.
수정주가 adjusted price
액면분할·유상증자로 주식 수가 바뀌면 과거 가격을 지금 기준으로 환산해야 차트가 안 튑니다. KIS 파라미터 FID_ORG_ADJ_PRC=0이 그걸 켭니다.
business day
lightweight-charts가 '2026-08-07' 같은 문자열 시각을 받으면 "영업일"로 알아듣고 주말·휴장일을 알아서 건너뜁니다. 숫자(유닉스 초)를 주면 그렇게 안 됩니다. 일봉엔 반드시 문자열을 줘야 합니다.
유닉스 시간 unix timestamp
1970-01-01 UTC부터 흐른 초. 시간 계산·비교가 쉬워서 차트 라이브러리가 이걸 씁니다.
UTC / KST
UTC는 세계표준시, KST는 한국시간 = UTC+9. 원격 DB 서버는 UTC, 우리 데이터는 KST → 이 9시간 차이가 이 프로젝트 버그의 단골 원인입니다.
자가 치유 self-healing
분봉 테이블을 읽고, 그 뒤 구간만 원시 로그로 즉석 보강하는 설계. 수집기가 잠깐 죽어 있었어도 차트에 구멍이 안 생깁니다.
경계 잠금 fixLeftEdge / fixRightEdge
차트를 데이터 바깥으로 못 끌어내게 막는 옵션. 둘 다 켜야 "최대 축소 = 전체 데이터가 화면에 딱 참"이 됩니다. 하나만 켜면 여백이 다시 생깁니다.

8-1. 문제: 차트가 매일 아침 9시에 새로 시작했다

8-3. 자가 치유 — 수집기가 죽어 있어도 구멍이 안 난다

분/시간봉은 두 곳에서 읽어 이어 붙입니다:

  1. stock_candles_1m에서 읽어 버킷 단위로 묶습니다 (빠름).
  2. 그 분봉이 어디까지 있는지 확인하고, 그 뒤 구간만 stock_logs로 즉석 집계해 보강합니다.
  3. 경계를 >(초과)로 잡아 중복 캔들이 0이 되게 합니다.

덕분에 수집기를 며칠 꺼놨어도 차트는 이어져 보입니다. 다만 즉석 집계 구간이 길어질수록 느려집니다 — 실제로 분봉이 하루 멈춰 있을 때 1주 탭이 4.3초까지 느려졌다가, 정상 상태에서는 46ms였습니다. 차트가 갑자기 느려지면 "수집기가 죽었나?"를 먼저 의심하면 됩니다.

8-5. 델타(delta)가 필요한 이유

진행 중인 1분은 10초마다 여러 번 DB에 씁니다. 그때 거래량을 "총합"으로 보내면:

[잘못된 방식 — 총합을 보냄] 10:00:10 총합 100 저장 → DB: 100 10:00:20 총합 250 저장 → DB: 100 + 250 = 350 ← 틀림! (실제는 250) 10:00:30 총합 400 저장 → DB: 350 + 400 = 750 ← 더 틀림 [올바른 방식 — 늘어난 몫(델타)만 보냄] 10:00:10 델타 100 저장 → DB: 100 내보낸 뒤 0으로 리셋 10:00:20 델타 150 저장 → DB: 100+150=250 ✅ 10:00:30 델타 150 저장 → DB: 250+150=400 ✅

8-7. 타임존 — 9시간이 조용히 갉아먹은 것들

실제로 터진 버그: 실시간 차트 갱신이 조용히 안 먹고 있었습니다.
서버가 주는 캔들 시간축은 "KST 벽시계를 UTC로 읽은 값"인데, 웹소켓의 created_at은 진짜 UTC(toISOString())였습니다. 두 값이 정확히 9시간 어긋나서, 새 캔들이 slot > last.time 조건에 걸려 전부 버려졌습니다. 에러도 안 나고요.
→ 해결: 실시간 시각에 KST_OFFSET = 9*3600을 더해 축을 맞춤.

타임존 규칙 3가지 (이것만 지키면 이 계열 버그가 안 납니다):

  1. 날짜·구간 계산은 PHP date()가 아니라 DB NOW()/CURDATE()로.
  2. DB 커넥션마다 SET time_zone='+09:00'. (PHP는 db.php, Node는 db.js)
  3. Node에서 KST를 만들 땐 로컬 시간대에 의존하지 말고 UTC에 9시간을 직접 더한 뒤 getUTC*()로 읽기.

SECTION 12실무 원칙 12가지

  1. 화면은 DB를 기다리지 않는다. 저장이 느려도 사용자 경험은 안 느려져야 합니다.
  2. 클라이언트 값은 안 믿는다. 가격도 수량도 서버가 다시 확인합니다.

  4. 시각은 DB에게 묻는다. PHP·Node·DB의 시계가 다 다릅니다.
  5. 스키마는 코드가 만든다. "형이 SQL 돌려야 함"은 다음 세션에서 잊힙니다.
  6. 역할을 데이터베이스 문법으로 못박는다. INSERT IGNORE 하나로 "정밀한 쪽이 이긴다"가 강제됩니다.

  8. 되돌릴 수 없는 건 드라이런부터. --dry 옵션을 먼저 만듭니다.

  10. 검증은 수치로 남긴다. "잘 됩니다"가 아니라 "41,638개 대조 불일치 0".
  11. 주석에 "왜"를 쓴다. "무엇을 하는지"는 코드가 말합니다. 주석은 왜 그렇게 했고 안 그러면 뭐가 깨지는지를 적습니다.
  12. 문서는 손으로 옮겨 적지 않는다. 빌더가 실제 파일을 읽게 하면 오타도, 옛 버전도 섞일 수 없습니다.

SECTION 13면접 예상질문 25개

Q1. 이 프로젝트를 한 문장으로 소개해주세요.
한국투자증권 오픈API로 실시간 시세를 받아, 가상 자금으로 매매를 체험하는 모의투자 웹서비스입니다. 실시간 데이터 처리와 시계열 데이터 압축이 핵심 기술 과제였습니다.
Q2. 왜 PHP와 Node.js를 같이 썼나요?
PHP는 요청-응답 후 종료되는 구조라 24시간 웹소켓 연결을 유지할 수 없습니다. 실시간 시세는 상주 프로세스가 필요해 Node로 분리했고, 화면·비즈니스 로직은 PHP가 맡습니다. 둘은 DB를 통해 만납니다.
Q3. 초당 수십 건씩 오는 실시간 데이터를 어떻게 처리했나요?
세 가지를 조합했습니다. ① 브라우저 전송을 DB 저장보다 먼저 해서 화면이 DB에 묶이지 않게 했고, ② 저장은 종목별 스로틀(원시 10초·현재가 1초)을 걸어 쓰기량을 체결량과 무관하게 고정했고, ③ 정밀도 손실은 메모리 분봉 누적으로 보완했습니다.
Q4. 스로틀을 걸면 고가·저가가 부정확해지지 않나요?
맞습니다. 그래서 분봉 누적만은 스로틀 앞에 뒀습니다. 모든 체결을 메모리에서 OHLC로 누적하고, DB 쓰기는 10초에 한 번 배치로 묶습니다. 저장량은 줄이면서 정밀도는 원본 그대로 유지됩니다.
Q5. 1년치 차트를 그리면 데이터가 너무 많지 않나요?
그래서 기간별로 해상도를 다르게 줍니다. 1일은 1분봉, 1주는 5분봉, 1개월 이상은 일봉입니다. 어느 탭을 눌러도 캔들이 수백 개로 유지돼서, 2년 보기가 오늘 보기보다 무겁지 않습니다. 1분봉으로 1년을 그렸다면 캔들 9만 개가 됐을 겁니다.
Q6. 같은 데이터를 테이블 3개에 중복 저장하는 게 낭비 아닌가요?
중복이 아니라 정밀도와 크기의 교환입니다. 원시 틱은 7일만 두고 지웁니다. 1분봉은 원본의 1/35 크기로 몇 달, 일봉은 하루 1행이라 몇 년을 보관합니다. 오래된 데이터일수록 굵은 해상도로 남기는 건 시계열 DB의 일반적인 전략(다운샘플링)이기도 합니다.
Q7. 오래된 원시 데이터를 지울 때 위험하지 않았나요?
복구가 불가능해서 안전장치를 세 겹 뒀습니다. ① 그날 분봉 커버리지가 90% 미만이면 그날은 건너뜁니다. ② --dry로 무엇이 지워질지 먼저 출력합니다. ③ 5만 행씩 청크로 지워 락이 오래 걸리지 않게 했습니다.
Q8. 매수 로직에서 동시성 문제는 어떻게 막았나요?
트랜잭션 안에서 SELECT ... FOR UPDATE로 잔고 행을 잠급니다. 잠그지 않으면 잔고 100만원으로 동시에 두 번 매수해서 잔고가 마이너스가 될 수 있습니다. 예외가 나면 rollback으로 전부 되돌립니다.
Q9. 평균단가는 어떻게 계산하나요?
(기존수량×기존평단 + 신규수량×신규가) ÷ 총수량입니다. 이동평균 방식이라 매수할 때마다 갱신됩니다. 전량 매도하면 보유 행 자체를 삭제합니다.
Q10. 그러면 과거 시점의 평균단가는 어떻게 아나요?
DB에 없습니다. holdings.avg_price는 '지금' 값이고 전량 매도하면 행이 사라지니까요. 그래서 거래내역의 실현수익률은 주문을 시간순으로 재생(replay)해서 매 시점 평단을 복원해 계산합니다. 매수는 원가에 더하고, 매도는 그 시점 평단으로 손익을 확정하는 방식입니다.
Q11. SQL 인젝션은 어떻게 막았나요?
prepared statement를 씁니다. SQL 틀을 먼저 보내고 값을 따로 보내므로, 값이 SQL 문법으로 해석될 수 없습니다. 이스케이프 함수로 막는 것보다 원리적으로 안전합니다.
Q12. CSRF는 어떻게 막았나요?
세션에만 존재하는 난수 토큰을 폼에 심고 서버에서 대조합니다. 외부 사이트는 세션 내용을 볼 수 없어 토큰을 만들 수 없습니다. 비교는 hash_equals()로 하는데, 일반 비교는 앞글자가 다르면 즉시 끝나서 응답 시간 차이로 토큰을 유추당할 수 있기 때문입니다.
Q13. 관리자 권한은 어떻게 관리하나요?
역할 기반(RBAC)입니다. 역할별 권한 목록을 두고 adminCan()으로 확인합니다. 중요한 건 화면에서 버튼을 숨기는 것만으론 부족하다는 점이라, 액션 핸들러에서 requireAdminCan()으로 서버가 다시 막습니다. 세션 이름도 유저와 분리해서 한쪽 로그인이 다른 쪽 권한이 되지 않게 했습니다.
Q14. 가장 어려웠던 버그는 무엇인가요?
타임존 버그입니다. 실시간 차트 갱신이 안 되는데 에러가 하나도 안 났습니다. 서버 캔들의 시간축은 'KST를 UTC로 읽은 값'이고 웹소켓 시각은 진짜 UTC라 정확히 9시간이 어긋났고, 새 캔들이 조건문에서 전부 버려지고 있었습니다. 이후로는 시각 계산을 전부 DB 시계 기준으로 통일했습니다.
Q15. 에러 없이 틀리는 버그를 또 겪은 적 있나요?
있습니다. GROUP_CONCAT의 기본 길이 제한 1024바이트에 걸려 30분봉의 시가·종가가 잘린 값으로 계산됐습니다. 경고조차 없었습니다. 그래서 분봉 41,638개를 원본 틱과 전수 대조해 불일치 0을 확인하는 검증을 넣었습니다.
Q16. 수집기가 죽었는지 어떻게 판단하나요?
프로세스 목록이 아니라 DB의 최근 60초 행수로 봅니다. 실제로 프로세스 조회가 신뢰되지 않아 살아 있는 수집기를 죽었다고 오판한 적이 있습니다. 간접 신호보다 직접 증거를 보는 게 맞습니다. 추가로 장중에 체결이 120초간 없으면 스스로 세션을 재접속하는 워치독도 있습니다.
Q17. 외부 API 제한은 어떻게 다뤘나요?
세 가지입니다. ① 액세스 토큰을 23시간 캐싱해 발급 횟수를 줄였고, ② 초당 제한 에러(EGW00201)가 오면 0.7초 후 최대 3회 재시도하며, ③ 웹소켓 구독은 세션당 약 41건 제한이 있어 상위 40종목만 실시간으로 받고 나머지는 REST로 보충합니다.
Q18. 실시간 구독을 40개만 하면 상세 페이지는 어떻게 하나요?
종목 상세를 열면 watch 메시지로 그 종목을 동적으로 구독 추가하고, 떠나면 해제합니다. 여러 사람이 같은 종목을 보고 있을 수 있어 refcount로 세고, 0이 될 때만 실제로 해제합니다.
Q19. 장 마감 후에 화면이 비지 않나요?
REST로 초기 로드를 하고 웹소켓은 그 위에 갱신만 얹는 2단 구조라, 장이 닫혀 있어도 마지막 상태가 그대로 보입니다.
Q20. 과거 데이터는 어떻게 채웠나요?
KIS 일봉 API로 백필했습니다. 실호출로 확인해보니 한 번에 정확히 100행이고, 구간을 길게 줘도 끝 날짜 기준 최근 100행만 줍니다. 그래서 끝 날짜를 뒤로 밀어가며 반복 호출하는 스크립트를 만들었습니다. 무한루프를 막는 가드도 넣었습니다.
Q21. 마이그레이션 없이 스키마가 바뀌면 어떻게 하나요?
코드가 스스로 보강합니다. CREATE TABLE IF NOT EXISTS와, 컬럼은 information_schema로 존재를 확인한 뒤 ALTER 합니다. ADD COLUMN IF NOT EXISTS는 MariaDB 전용이라 MySQL에서는 못 씁니다. 배포 시 수동 SQL 단계를 없애는 게 목적입니다.
Q22. 테스트는 어떻게 했나요?
분봉 로직을 순수 함수 모듈로 분리해서 웹소켓 없이 실행할 수 있게 만들고, 회귀 테스트 39개를 붙였습니다. 타임존, OHLC 정확성, 이상치 방어, 델타 중복 방지, 메모리 정리, 종목 독립성, 1만 건 부하까지 확인합니다. 돈이 걸린 숫자라 회귀 테스트가 꼭 필요하다고 판단했습니다.
Q23. 팀원과 DB를 공유한다고 했는데 충돌은 없나요?
파이썬 팀원과 같은 MySQL을 씁니다. 테이블 이름 규칙이 갈려 있어(py_* 계열 vs stock_* 계열) 사실상 분리돼 있습니다. 다만 서버 시계가 UTC라 우리 KST 로직과 어긋나는 문제가 있어, 커넥션마다 세션 타임존을 KST로 고정했습니다. 용량도 공유 자원이라 원시 로그 정리 정책을 따로 만들었습니다.
Q24. 성능 개선 사례가 있나요?
분봉 저장을 종목별 개별 INSERT에서 한 방의 multi-row INSERT로 묶었습니다. 원격 DB는 왕복만 6ms라 40종목을 나눠 보내면 그것만 0.24초가 날아갑니다. 또 차트 조회는 분봉 테이블을 읽게 바꿔서, 원시 로그 즉석 집계 대비 4.3초 → 46ms로 줄었습니다.
Q25. 앞으로 개선하고 싶은 부분은?
세 가지입니다. ① 자동매매 로직 — 화면과 DB 스키마는 준비돼 있고 매매 규칙만 붙이면 됩니다. ② 로그 로테이션 — 수집기 로그가 150MB를 넘겼습니다. ③ 시크릿을 파일 평문에서 환경변수로 분리하는 것입니다. 지금은 .htaccess로 막고 있지만 방어가 한 겹뿐입니다.
